# 链路上下文接入指南

本文说明如何在 HTTP 服务、定时任务、消息监听、异步 goroutine 中接入统一的链路上下文，以及日志如何自动输出 `{trace_id}` 与 `<request_id>`。

---

## 概念

| 标识 | 作用域 | 说明 |
|------|--------|------|
| **trace_id** | 每个最小执行单元 | 一次 HTTP 请求、一次定时触发、一条消息消费、一个独立后台任务各有一个 trace。跨服务通过 `X-Trace-Id` 传递。 |
| **request_id** | 仅 HTTP 入站 | 单次 HTTP 请求的唯一 ID，用于幂等/去重。通过 `X-Req-Id` 传递。定时器、监听器**没有** request_id。 |

**设计原则**

- 上游有 header 则透传，没有则自动生成（trace 在 Header 中间件阶段即补齐）。
- 日志、错误、下游调用都应携带 `context.Context`，以便 ID 自动传播。
- 业务代码**不需要**手动拼 `trace_id=` 前缀，logger 会自动格式化。

---

## 包职责

| 包 | 职责 |
|----|------|
| `ctx/` | 对外入口：`Run` / `Go` / `Fork` / `GetTraceId` / `GetReqId` / `ContinueTrace` |
| `trace/` | trace 实现：ID 生成、延续、OTEL 对齐（业务一般不需要直接 import） |
| `request/` | HTTP 专有：`ApplyHTTP`、`GenerateRequestID`、Header 常量 |
| `logger/` | 日志：`MetaHandler` 输出 `{trace_id}` `<request_id>` |
| `middleware/` | 共享 Header 绑定表；`goframe` / `ugin` 提供框架中间件 |

业务侧推荐只 import **`ctx`** 和 **`logger`**；HTTP 服务注册中间件即可。

## 日志格式

```text
# HTTP 请求（有 trace + request）
[INFO] {deadbeefdeadbeefdeadbeefdeadbeef} <202508271200001a2b3c4d5e6f> 业务消息

# 定时器 / 监听器（仅 trace）
[INFO] {deadbeefdeadbeefdeadbeefdeadbeef} 定时结算完成

# 无 ctx ID
[INFO] 业务消息
```

**打日志**：始终传入 `context.Context`：

```go
import "github.com/hosgf/element/logger"

logger.Infof(c, "处理完成 orderId=%s", orderId)
```

多文件 / 分类日志：

```go
logger.Named("pay").Infof(c, "支付回调")
logger.New(customGlog).Infof(c, "写入独立文件")
```

## HTTP 接入

### GoFrame

```go
import (
    "github.com/gogf/gf/v2/net/ghttp"
    mf "github.com/hosgf/element/middleware/goframe"
)

func main() {
    s := ghttp.GetServer()
    mf.SetMiddleware(s, mf.Recover)

    s.BindHandler("/api/demo", func(r *ghttp.Request) {
        logger.Infof(r.Context(), "handle demo")
    })
    s.Run()
}
```

中间件顺序（`SetMiddleware` 内部固定）：

1. `MiddlewareGzip` — 最外层，按 `Accept-Encoding` 压缩
2. `MiddlewareCORS`
3. `MiddlewareHeader` — 请求头写入 ctx；trace 由 OTel 桥接
4. `MiddlewareCookies`
5. 业务中间件（`Recover`、`AccessLog`、`Dedup` 等）

`Recover` 补齐 `request_id`、回写响应头，并捕获 panic。Gzip / 访问日志 / 去重详见 [HTTP 中间件](./HTTP中间件.md)。

### Gin

```go
import (
    "github.com/gin-gonic/gin"
    mu "github.com/hosgf/element/middleware/ugin"
)

func main() {
    r := gin.New()
    mu.SetMiddleware(r, mu.ExceptionHandler())

    r.GET("/api/demo", func(c *gin.Context) {
        logger.Infof(c.Request.Context(), "handle demo")
    })
    _ = r.Run(":8080")
}
```

### 响应头

| Header | 说明 |
|--------|------|
| `traceparent` | W3C 链路（OTel 传播） |
| `X-Req-Id` | 请求 ID（HTTP 才有） |
| `X-Response-Time` | 请求耗时 |

### 读取 ID

```go
import "github.com/hosgf/element/ctx"

tid := ctx.GetTraceId(c)
rid := ctx.GetReqId(c)
```

错误处理中也可使用 `uerrors.GetRequestID(c)`（语义 key 优先，其次 `X-Req-Id` header key）。

## 非 HTTP 场景

定时器、消息监听：**每次触发是新执行单元，需要新 trace**。

```go
import (
    "context"
    "github.com/hosgf/element/ctx"
    "github.com/hosgf/element/logger"
)

func onCronTick() {
    ctx.Run(context.Background(), func(c context.Context) {
        logger.Infof(c, "定时结算")
    })
}

func onMessage(parent context.Context, msg []byte) {
    ctx.Run(parent, func(c context.Context) {
        logger.Infof(c, "消费消息")
    })
}
```

### 异步 goroutine

HTTP 请求内：**继承 trace（及 request_id），不受请求 cancel 影响**。

```go
func handle(c context.Context) {
    ctx.Go(c, func(child context.Context) {
        logger.Infof(child, "异步通知")
    })
}
```

手动控制：

```go
go func() {
    child := ctx.Fork(parent)
    logger.Infof(child, "manual async")
}()
```

## 场景对照

| 场景 | 用法 | trace | request_id |
|------|------|-------|------------|
| HTTP 入站 | 注册 middleware，用 `r.Context()` / `c.Request.Context()` | 自动 | 自动 |
| 定时器 / 监听 | `ctx.Run(c, fn)` | 每次新开 | 无 |
| HTTP 内 goroutine | `ctx.Go(c, fn)` | 继承 | 继承（若有） |
| 出站 HTTP | `httputil` 或 `request.Inject` / `Outbound` | 透传 | 透传（若有） |

---

## 出站 HTTP 透传

推荐用 `httputil`（已自动注入）。自建 client 时：

```go
import "github.com/hosgf/element/client/request"

// 方式 1：按当前 ctx 写入链路头（覆盖同名头）
request.Inject(req.Header, c)

// 方式 2：只要链路头 map
headers := request.Outbound(c) // map: X-Trace-Id, X-Req-Id（有则带）

// 方式 3：全量业务头（含租户等）+ 链路语义键回退
headers := request.GetHeader(c)
```

`Outbound` / `HeaderTraceId.Get` 会从语义键 `trace_id` / `request_id` 读取，  
因此 `ctx.Run` 后出站也能带上 `{trace_id}`，不依赖中间件是否写过 `X-Trace-Id` 键。

## 与异常处理配合

全局异常中间件从 ctx 读取 `request_id` 写入 `BizError.RequestID` 和日志。业务抛错时无需手动设置 ID，保证 ctx 从入口一路传递即可。

详见 [全局异常处理.md](./全局异常处理.md)。

## 常见问题

**Q: 为什么定时任务没有 `<request_id>`？**

request_id 仅表示一次 HTTP 请求。定时/监听只有 `{trace_id}`。

**Q: 没挂 Recover / ExceptionHandler 会怎样？**

Header 中间件仍会生成 trace，但 **request_id 不会生成**，panic 也不会被统一捕获。

**Q: GoFrame 日志里出现两套 trace？**

GoFrame 内置 `ServerTracing` 会额外注入 OTEL `{traceId}`。若重复，可关闭 GoFrame 自带 tracing，或只保留 element 一套。

**Q: 本地调试如何构造 ctx？**

```go
import "github.com/hosgf/element/types"

c := context.WithValue(context.Background(), types.TraceIdKey, "deadbeefdeadbeefdeadbeefdeadbeef")
c = context.WithValue(c, types.RequestIdKey, "req-001")
logger.Infof(c, "hello")
```
